# 機能設計書

Waders の機能と業務ルール（画面に依らない振る舞い）を定める。実装（`src/server/domain/`・`src/server/application/`・`src/server/presentation/`）と常に一致させる。画面は [画面設計書](画面設計書.md)、保存するデータは [データ設計書](データ設計書.md) を参照。

## 1. 機能の一覧

| 番号 | 機能 | 内容 | issue |
| --- | --- | --- | --- |
| F-01 | 商品の登録・編集・削除・一覧 | 商品の入力を検証して保存する。一覧は登録順 | #7・#8 |
| F-02 | ステータスの自動遷移 | 発売月・受注期限の超過で、ステータスを自動で変える | #9 |
| F-03 | アーカイブ | 発売月が当月より前の商品を、リストとは別に表示する | #9 |
| F-04 | リストに戻す | アーカイブされた商品を、新しい発売月でリストに戻す | #9 |
| F-05 | 延期の確認 | 自動で購入済になった予約商品が届いたかを確かめる | #9 |
| F-06 | カテゴリー | 定義のファイルのカテゴリーを商品に設定し、リストとアーカイブを絞り込む。画面からカテゴリーを追加・改名・削除し、定義にないカテゴリーの商品の扱いを決める | #10 |

## 2. 業務ルール

日・月の判定はすべて日本時間（Asia/Tokyo）の暦で行う。現在時刻はアプリケーション層の `Clock` から受け取る。

| 番号 | ルール | 実装 |
| --- | --- | --- |
| BR-01 | **発売月の超過**: 発売月の翌月 1 日 0:00 になったら超過とする（例: 発売月 2026-11 は 2026-12-01 0:00 から超過） | `isProductArchived` |
| BR-02 | **予約済の自動遷移**: 発売月を超過したら購入済にし、延期の確認待ちにする。受注期限は見ない | `determineAutomaticTransition` |
| BR-03 | **検討中の自動遷移**: 受注期限の翌日 0:00 になるか、発売月を超過したら未購入にする（受注期限がまだ先でも、発売月を超過したら未購入）。延期の確認待ちにはしない | `determineAutomaticTransition` |
| BR-04 | **購入済・未購入**: 自動では変えない（手で購入済にした商品は延期の確認の対象外） | `determineAutomaticTransition` |
| BR-05 | **アーカイブ**: 発売月が当月より前の商品は、ステータスにかかわらずアーカイブとする。アーカイブかどうかは保存せず、その都度求める | `isProductArchived`・`splitProductsByArchive` |
| BR-06 | **リストに戻すときのステータス**: 変更履歴の最後のステータスの変更が自動遷移なら、その変更前のステータスに戻す。最後の変更が利用者の操作なら、今のステータスのまま | `determineStatusBeforeAutomaticTransition` |
| BR-07 | **新しい発売月**: リストに戻す・延期の確認の「延期された」で指定する発売月は、当月以降とする | `restoreProduct`・`answerDeliveryConfirmation` |
| BR-08 | **アーカイブされた商品の編集**: 発売月以外は編集できる。発売月は編集では変えられず、リストに戻すで変える。編集でステータスを変えたら延期の確認待ちを外す | `updateProduct` |
| BR-09 | **カテゴリーの定義が正**: 商品に新しく設定できるのは、定義にあるカテゴリーだけ。商品には ID と、設定したときの名前を保存する | `createProduct`・`updateProduct` |
| BR-10 | **カテゴリー名の表示**: 定義にある ID は定義の今の名前で、定義にない ID は最後に保存した名前で示す（画面では「（定義にない）」を付ける） | `listProducts`・`buildCategoryFilterOptions` |
| BR-11 | **壊れた定義**: 定義のファイルに誤りがある間は、カテゴリーの設定と絞り込みはできない（理由を画面に表示する）。カテゴリーを変えない編集と、カテゴリーのない登録はできる。壊れたファイルは書き換えない | `readCategories`・`resolveCategory` |
| BR-12 | **絞り込み**: 選んだカテゴリーの商品だけを表示し、見出しの個数と合計金額も絞り込んだ商品で数える。何も選ばなければすべて。選択は端末ごとに覚え、選択肢にないものは選んでいないものとする | `filterProductsByCategory`・`useCategoryFilter` |
| BR-13 | **発売月の移動**: 移動できるのはアーカイブされていない商品だけで、移動先は当月以降。同じ月への移動は何もしない（履歴も記録しない）。変更は利用者の操作として記録する | `moveProductToReleaseMonth` |
| BR-14 | **カテゴリーの管理は最新の定義に対して**: 追加・改名・削除は、変更する時点の定義のファイルを読み直して行い、手で編集した内容（ID のないカテゴリー・ほかの項目）を残す。新しいカテゴリーは末尾に加える。名前は定義の中で重複させない。改名・削除するカテゴリーが最新の定義にない場合は変更しない | `addCategory`・`renameCategory`・`deleteCategory`（定義のファイル） |
| BR-15 | **改名への追従**: 改名したら、そのカテゴリーの商品に保存している名前も新しい名前にする（更新日時は変えない） | `renameCategory` |
| BR-16 | **カテゴリーの削除**: そのカテゴリーの商品（アーカイブを含む）を、移す先（定義のほかのカテゴリー）かカテゴリー未設定にしてから、定義から取り除く。移した商品の更新日時は移した時刻にする。カテゴリーの付け替えは変更履歴（ステータス・発売月）に記録しない | `deleteCategory` |
| BR-17 | **定義にないカテゴリー**: 定義にない ID の商品は、「定義に追加する」（同じ ID と、商品に最後に保存した名前で末尾に加える。同じ名前が定義にあれば加えない）か、すべての商品を定義のカテゴリーに移す・カテゴリー未設定にする | `addUndefinedCategoryToDefinition`・`reassignUndefinedCategoryProducts` |
| BR-18 | **認証が必要な範囲**: 認証が有効なときは、`/api/health` と `/api/auth/*` 以外の API にログインを求める。画面のファイル（HTML・JS・CSS）は認証なしで返し、画面がログインの画面を表示する（データはすべて API から取る）。認証が無効なときは誰でも使える | `createAuthenticationRequirement` |
| BR-19 | **アカウントは1つ**: アカウントがないときだけ作れる（ID は前後の空白を除いて1〜50文字、パスワードは8〜128文字）。2つ目は作れない | `setUpAccount` |
| BR-20 | **ログインした状態の期間**: 最後に使ってから30日。使うたびに延ばし、Cookie の有効期間も付け直す。30日使わなかった状態は使えない | `verifySession`・`isSessionExpired` |
| BR-21 | **総当たり対策**: 同じ接続元（IP アドレス）からログインに5回続けて失敗すると、5回目の失敗から15分間、その接続元からは ID とパスワードが正しくてもログインできない。失敗の回数と制限は接続元ごとに数え、ほかの接続元の失敗では制限しない（issue #36）。IPv4 のアドレスと、それを IPv6 の形で表したもの（`::ffff:192.168.1.5`）は同じ接続元とする。成功すると、その接続元の回数だけを数え直す。ID が誤りの失敗も数える。失敗の記録はメモリに持ち、再起動・アカウントの消去で数え直す | `recordLoginFailure`・`findLoginLockEnd` |
| BR-22 | **失敗の理由を示さない**: ID が誤りの場合もパスワードが誤りの場合も、同じ応答を返す。ID が誤りの場合もパスワードの比較と同じだけ時間をかける | `logIn` |
| BR-23 | **アカウントの消去**: パスワードを忘れた場合は、コマンド（`npm run reset-account`）でアカウントとすべてのログインした状態を消す。商品・カテゴリーなどは消さない | `resetAccount` |
| BR-24 | **入力項目の出し入れ**: 出し入れする項目は、送料・メーカー・受注期限・キャンセル可否・場所・開催日時と終了日時（1 組）・手数料・交通費（見込）・その他費用。表示するのは、カテゴリーで有効な項目と、編集のモーダルを開いた時点で値が保存されている項目（キャンセル可否は「可」、開催日時と終了日時はどちらかに値がある場合）。カテゴリー未設定・定義にないカテゴリーは既定（送料・メーカー・受注期限・キャンセル可否）、定義を読めない間はすべてを有効とする。表示していない項目は未入力として送る。出し入れは画面だけで行い、API は値を拒否しない（定義は手で変わり得るため） | `determineVisibleCategoryFields`（画面） |
| BR-25 | **合計金額**: 見出しの合計は、金額・送料・手数料・交通費（見込）・その他費用の合計。金額が未入力の商品は個数だけに含め、費用も合計に含めない。未購入は含めない。開催日時は関係しない | `summarizeProducts`（画面） |
| BR-26 | **「その他費用」の名前**: カテゴリーごとに持ち（1〜20 文字。既定は「その他費用」）、商品には保存しない。カテゴリー未設定・定義にないカテゴリー・定義を読めない場合は「その他費用」 | `resolveOtherExpenseLabel`（画面） |
| BR-27 | **項目の設定の変更**: 画面からの変更は、変える時点の定義のファイルを読み直し、変えた項目だけを反映する（手で編集した内容を残す）。項目を変えたカテゴリーには有効な項目をすべて書き、名前を既定に戻すと名前を取り除く。項目の指定がないカテゴリー（今までの定義・画面で追加したカテゴリー）は既定とする。商品に保存されている値は変えない | `updateCategoryFieldSettings`（定義のファイル） |
| BR-28 | **開催日時の表示**: 開催日時と終了日時の両方があるときだけカードに示す。カードを並べる幅では日本時間の日時（「11/20 18:00〜21:00」。同じ日なら終了の日付を省き、年が変わるなら年も）、スマートフォンの幅のリスト形式では開催期間。期間は分を 30 分単位で四捨五入（半分は切り上げ、最小 0.5 時間）し、それが 24 時間以上（23 時間 45 分以上）なら 12 時間単位で四捨五入した日数で示す（「約1.5時間」「約2日」。整数なら小数を付けない） | `formatEventPeriod`・`formatEventDuration`（画面） |
| BR-29 | **接続を受け付ける名前**: Host ヘッダーの名前が IP アドレス（IPv4・IPv6）・`localhost`・`.local` で終わる名前・設定の `allowedHosts` のときだけ応答し、それ以外（Host がない・読めない場合を含む）は API・画面のファイルとも 403。大文字・小文字とポートは問わない。状態を変えるリクエスト（POST・PUT・PATCH・DELETE）で Origin ヘッダーがある場合は、Origin の「名前:ポート」が Host と一致するときだけ処理する（`null` は不一致）。設定の `hostValidationEnabled` が `false` なら確かめない（issue #35） | `validateHostAndOrigin`（webApplication.ts） |
| BR-30 | **画面と API を置くパス**: 画面と API は設定の `basePath`（既定 `/waders`。`""` は `/` の下）の下に置く。`/` と末尾の `/` がない `<basePath>` を GET・HEAD で開いた場合は `<basePath>/` へ 302 で転送し、パスの外のそれ以外の URL は 404。ログインした状態の Cookie の Path は `<basePath>`（`""` なら `/`）。画面は開いているページの場所から API の呼び先（`<basePath>/api/...`）を決める（issue #39） | `createBasePathRedirect`（webApplication.ts）・`resolveApiPath`（productApiClient.ts） |
| BR-31 | **商品の画像の受け付け**: 画像の形式は、拡張子や Content-Type ではなく中身の先頭の印で判定し、JPEG・PNG・WebP だけを受け付ける（GIF・SVG・テキストなどは 400）。中身が 2MB（2,097,152 バイト）を超えるものは 413。保存するファイルの名前は乱数の UUID と形式の拡張子にする（利用者の入力から作らない）。画像を付ける・消すことは商品の更新ではないため、更新日時と変更履歴は変えない。差し替え・削除・商品の削除では前のファイルを消す（issue #41） | `detectProductImageFormat`（productImage.ts）・`saveProductImage`（productService.ts） |
| BR-32 | **商品の画像の保存の順序**: モーダルの保存では、商品を保存してから画像を送る・消す（商品を保存できなければ画像は送らない）。画像だけを保存できなかった場合は、商品は保存したままモーダルを閉じ、画像を保存できなかったことを画面の下端の知らせで伝える（「保存して続けて追加」ではモーダルの中で伝える）。画像に触れていなければ画像の API は呼ばない（issue #41） | `saveProduct`（ProductEditorDialog.tsx） |

カテゴリーの改名・削除では、商品の更新と定義のファイルの書き込みを 1 つのトランザクションの中で行い、ファイルの書き込みを最後にする（書き込みに失敗したら商品の更新を取り消す）。

## 3. F-02 ステータスの自動遷移

- 判定の時期: 商品の一覧を取得するたび（`GET /api/products`）と、サーバーの起動時
- 遷移した場合は、変更履歴に種類「自動遷移」（`automatic`）、変更日時は判定した時刻で記録する
- 遷移の対象がなければ何も記録しない（何度一覧を取得しても履歴は増えない）
- 1 商品の遷移（ステータスの更新・履歴・延期の確認待ち）は 1 つのトランザクションで行う

```
            発売月を超過（BR-02）
  予約済 ─────────────────────────→ 購入済 ＋ 延期の確認待ち
            受注期限の翌日 or 発売月を超過（BR-03）
  検討中 ─────────────────────────→ 未購入
```

## 4. F-04 リストに戻す

1. 商品がアーカイブされていなければ拒否する（409 `PRODUCT_NOT_ARCHIVED`）
2. 新しい発売月が当月より前なら拒否する（400 `RELEASE_MONTH_IN_PAST`。BR-07）
3. ステータスを BR-06 で求め、発売月を新しい月にし、延期の確認待ちを外す。変更は利用者の操作（`user`）として記録する

## 5. F-05 延期の確認

| 回答 | 結果 |
| --- | --- |
| 届いた（`arrived`） | 購入済のまま（アーカイブに残る） |
| 延期された（`postponed`） | 新しい発売月（当月以降。BR-07）で予約済にする（リストに戻る） |
| 買わなかった（`notPurchased`） | 未購入にする（アーカイブに残る） |

- いずれの回答でも延期の確認待ちを外す。変更は利用者の操作（`user`）として記録する
- 確認待ちでない商品への回答は拒否する（409 `DELIVERY_CONFIRMATION_NOT_PENDING`）
- 画面は回答した商品だけを送る。回答しなかった商品は確認待ちのまま残り、次に開いたときにまた確かめる

## 6. API

パスはすべて設定の `basePath`（既定 `/waders`）の下にある（例: `GET /waders/api/products`。BR-30）。以下は `basePath` を除いたパスで書く。

| メソッド・パス | 内容 | 成功 |
| --- | --- | --- |
| `GET /api/products` | 自動遷移を反映した一覧。各商品に `deliveryConfirmationPending`（延期の確認待ちか）を含める | 200 `{ products }` |
| `POST /api/products` | 登録 | 201 |
| `PUT /api/products/:productId` | 編集（全項目） | 200 |
| `DELETE /api/products/:productId` | 削除 | 204 |
| `POST /api/products/:productId/restore` | リストに戻す。本文 `{ releaseMonth }` | 200 |
| `POST /api/products/:productId/delivery-confirmation` | 延期の確認への回答。本文 `{ answer: 'arrived' }`・`{ answer: 'postponed', releaseMonth }`・`{ answer: 'notPurchased' }` | 200 |
| `PATCH /api/products/:productId/release-month` | 発売月だけを変える（ドラッグアンドドロップ・元に戻す）。本文 `{ releaseMonth }`。ほかの項目は変えない（BR-13） | 200 |
| `PUT /api/products/:productId/image` | 画像を付ける・差し替える。本文 `{ data }`（画像の中身の base64）。応答は画像を付けた商品（BR-31） | 200 |
| `DELETE /api/products/:productId/image` | 画像を消す。画像がなくても成功する | 204 |
| `GET /api/products/:productId/image` | 画像の中身。Content-Type は中身から判定した形式（`image/jpeg`・`image/png`・`image/webp`） | 200 |
| `GET /api/categories` | カテゴリーの定義（並び順のまま）。本文 `{ categories: [{ id, name, fields, otherExpenseLabel }] }`（`fields` は有効な入力項目、`otherExpenseLabel` は「その他費用」の名前。#27） | 200 |
| `POST /api/categories` | カテゴリーを定義の末尾に加える。本文 `{ name }`。応答は加えたカテゴリー（BR-14） | 201 |
| `PUT /api/categories/:categoryId` | カテゴリーを改名する。本文 `{ name }`。応答は改名したカテゴリー（BR-14・BR-15） | 200 |
| `DELETE /api/categories/:categoryId` | カテゴリーを削除する。本文 `{ moveToCategoryId }`（`null` はカテゴリー未設定にする）（BR-16） | 204 |
| `POST /api/categories/:categoryId/add-to-definition` | 定義にないカテゴリーを定義に加える。応答は加えたカテゴリー（BR-17） | 201 |
| `POST /api/categories/:categoryId/reassign-products` | 定義にないカテゴリーの商品を付け替える。本文 `{ moveToCategoryId }`（BR-17） | 204 |
| `PATCH /api/categories/:categoryId/field-settings` | 入力する項目と「その他費用」の名前を変える。本文 `{ fields?: { location: true, ... }, otherExpenseLabel?: string \| null }`（変える項目だけ。null は「その他費用」に戻す）。応答は変更したカテゴリー（BR-27） | 200 |
| `GET /api/auth/status` | 認証の状態 `{ authenticationEnabled, accountExists, loggedIn }`。ログインしていなくても使える（BR-18） | 200 |
| `POST /api/auth/setup` | アカウントを作り、ログインした状態の Cookie を付ける。本文 `{ loginId, password }`（BR-19） | 201（状態） |
| `POST /api/auth/login` | ログインし、Cookie を付ける。本文 `{ loginId, password }`（BR-21・BR-22） | 200（状態） |
| `POST /api/auth/logout` | ログインした状態を消し、Cookie を消す（ほかの端末のログインは残す） | 204 |

商品の登録・編集の本文ではカテゴリーを `categoryId`（未設定は `null`）で送り、応答では `categoryId` と `categoryName` を返す（#10）。場所・費用は `location`・`handlingFee`・`travelExpense`・`otherExpense`、開催日時・終了日時は `eventStartsAt`・`eventEndsAt`（UTC の ISO 8601）で送受する（#26・PR #30）。商品の応答には、画像の URL `imageUrl`（`/api/products/:productId/image?v=<版>`。画像を付け直すたびに版が変わる。画像がなければ `null`）を含める（#41）。

エラーの応答（本文は `{ error: { code, message, fieldErrors? } }`）:

| 状態 | コード | 場面 |

## 7. F-08 認証

- **設定**: 設定ファイルの `authenticationEnabled`（環境変数 `WADERS_AUTHENTICATION_ENABLED` が優先。`true`・`false` のみ）。ひな形では `false`（issue #33）。項目がない既存の設定ファイルは有効として扱う（安全側に倒す）
- **パスワードの保存**: `crypto.scrypt`（N = 16384、r = 8、p = 1、ソルト 16 バイト、長さ 32 バイト）のハッシュ値を、パラメーターとソルトと一緒に保存する。比較は `timingSafeEqual`
- **ログインした状態**: 乱数 32 バイトの値を Cookie `waders_session` に入れる（`HttpOnly`・`SameSite=Strict`・`Path` は `basePath`（`""` なら `/`。BR-30）・`Max-Age` 30日）。DB にはその値の SHA-256 だけを保存する。HTTPS の仕組みがないため `Secure` は付けない
- **CSRF**: 状態を変えるリクエスト（ログイン・ログアウトを含む）は `Content-Type: application/json` を必須にする（既存の決まり）。Cookie は `SameSite=Strict`
- **同時のログイン**: ログインの試行は1つずつ順に処理する（同時に送られた試行で BR-21 の回数をすり抜けさせない）
- **接続元**（BR-21。issue #36）: TCP の接続元（`request.socket.remoteAddress`）を使う。リバースプロキシを使わないため、偽装できる `X-Forwarded-For` や Express の `trust proxy` は使わない。接続元が分からない場合（接続が切れた後など）は、分からないものどうしを1つの接続元として数える
- **失敗の記録の片付け**（BR-21。issue #36）: 制限が解けた記録と、制限せずに最後の失敗から24時間たった記録は、ログインの試行のたびに捨てる（失敗の間が24時間以上空いた場合は、1回目から数え直す）。記録する接続元は1000までとし、上限に達した後に新しく失敗した接続元は、まとめて1つの接続元として数える（記録を追い出すと、追い出された接続元が制限をすり抜けられるため。持ち主の接続元にすでに記録があれば、その記録で判定する）

## 8. F-10 外部のサイトからの不正な接続の防止

- **目的**: 攻撃者のドメインの名前解決を、ページを開かせた後で Waders の IP アドレスに切り替える（DNS リバインディング）と、ブラウザからは同じオリジンへの通信に見えるため、`Content-Type: application/json` の必須（CSRF 対策）や CORS では防げない。ブラウザはこのとき攻撃者のドメインを Host に付けるため、Host を許した名前に限って防ぐ（BR-29）
- **設定**: `settings.json` の `allowedHosts`（ホスト名の配列。小文字にそろえる。ポート・URL・空白を含む値は設定の誤りとして起動を止める）と `hostValidationEnabled`（真偽値）。ひな形は `[]` と `true`。項目がなければ追加の名前なし・有効（安全側に倒す）。環境変数では切り替えない
- **順序**: セキュリティヘッダーを付けた直後、API と画面のファイルの配信より前に確かめる（403 の応答にも CSP を付ける）
- **開発時**: Vite のプロキシは `changeOrigin: false` で Host を `localhost:5173` のまま送る（vite.config.ts）。画面の Origin も `http://localhost:5173` のため、追加の設定なしで使える（`changeOrigin` を有効にすると Host がサーバーのポートに書き換わり、Origin と一致せず 403 になる）
- **無効にする場合**: リバースプロキシなどでインターネットに公開し、宛先の名前を前もって決められない場合。無効にしても `Content-Type` の確認（415）は残る

## 9. F-11 画面と API を置くパス

- **目的**: Raspberry Pi で `http://raspberrypi.local:8080/waders/` から開けるようにする。ポート 80 は Homebridge のイメージの nginx が使っていて、その設定は変えないため、ポートは残してパスだけを変える（issue #39）
- **設定**: `settings.json` の `basePath`。`""` か、`/` で始まる区切りの並び（英数字と `-`・`_`・`.`・`~`。`.`・`..` だけの区切り、末尾の `/`、`/` だけは不可）。誤った値は設定の誤りとして起動を止める。ひな形は `"/waders"`。項目がなければ `/waders`（更新するだけで新しい URL になる）。環境変数では切り替えない
- **サーバー**: Host・Origin の確認（BR-29）の後に `/` と `<basePath>` を転送し、画面と API をまとめたルーターを `<basePath>` に置く。画面の入り口（index.html）は、区切り `api` を含まない URL にだけ返す（パスの外の API の URL を画面と取り違えないため）
- **転送**: 302 にする。301 だとブラウザが覚え、設定を変えた後も古い転送が残るため
- **画面**: ビルド（Vite）は `base: './'` で、部品のファイルを相対パスで読み込む。API は `new URL('./api/...', document.baseURI)` で呼び先を決める。そのため、画面を作り直さずに `basePath` だけで変わる。画面の URL は1段（`/waders/archive` など）までを想定する
- **開発時**: 画面は今までどおり `http://localhost:5173/` で開く。Vite のプロキシは `/api` を、サーバーの `<basePath>/api` へ書き換えて転送する（vite.config.ts）

## 10. F-12 商品の画像

- **画面での準備**: 選んだ画像を `createImageBitmap`（写真の向きを反映）で読み、縦横の比を保って長い辺を 800px 以内に縮め（大きくはしない）、白の背景に重ねて JPEG（画質 0.85）にする。写真の位置情報などはこのとき消える。読めないファイルは欄の下に知らせ、送らない
- **プレビュー**: CSP で `data:`・`blob:` の画像を禁止しているため、選んだ画像は canvas に描く。編集では今の画像を API から読んで表示する
- **送り方**: 本文は JSON の `{ data }`（base64）。状態を変えるリクエストの `Content-Type: application/json` の必須（CSRF 対策）をそのまま使うため、multipart にはしない。本文の大きさの上限は API 全体で 100kb、画像を付ける API だけ 3MB（2MB の画像の base64 が入る大きさ）
- **保存先**: データのフォルダの `images`（所有者だけが使える 0700。最初の保存のときに作る）。ファイルは 0600。DB には商品ごとにファイルの名前だけを記録し、DB の CHECK 制約でも保存した形（UUID と拡張子）の名前に限る（フォルダの外を指さないため）
- **配信**: 画像の応答にもすべての応答と同じセキュリティヘッダー（`default-src 'none'` の CSP・`nosniff`）を付ける。認証が有効なときはログインを求める。`imageUrl` の版が今の画像と同じなら長く覚えさせ（`private, max-age=31536000, immutable`）、版がない・古い URL は毎回確かめさせる（`private, no-cache`）
- **表示**: カードとリストでは切らずに枠の中に収める（`object-fit: contain`）。画像を読み込めなかった場合は共通のアイコンにする（画像を付け直して URL が変われば、読み込み直す）
