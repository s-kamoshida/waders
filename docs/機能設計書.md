# 機能設計書

Waders の機能と業務ルール（画面に依らない振る舞い）を定める。実装（`src/server/domain/`・`src/server/application/`・`src/server/presentation/`）と常に一致させる。画面は [画面設計書](画面設計書.md)、保存するデータは [データ設計書](データ設計書.md) を参照。

## 1. 機能の一覧

| 番号 | 機能 | 内容 | issue |
| --- | --- | --- | --- |
| F-01 | 商品の登録・編集・削除・一覧 | 商品の入力を検証して保存する。一覧は登録順 | #7・#8 |
| F-02 | ステータスの自動遷移 | 発売月・受注期限の超過で、ステータスを自動で変える | #9 |
| F-03 | アーカイブ | 発売月が当月より前の商品を、リストとは別に表示する | #9 |
| F-04 | リストに戻す | アーカイブされた商品を、新しい発売月でリストに戻す | #9 |
| F-05 | 延期の確認 | 自動で購入済になった予約商品が届いたかを確かめる | #9 |
| F-06 | カテゴリー | 定義のファイルのカテゴリーを商品に設定し、リストとアーカイブを絞り込む。画面からカテゴリーを追加・改名・削除し、定義にないカテゴリーの商品の扱いを決める | #10 |
| F-07 | 発売月の移動 | リストの上で商品をドラッグアンドドロップして発売月を移動し、元に戻せる | #13 |

| F-09 | カテゴリーごとの入力項目 | 場所・費用・開催日時と終了日時の項目を持ち、カテゴリーごとに入力する項目と「その他費用」の名前を決める | #26・#27 |

## 2. 業務ルール

日・月の判定はすべて日本時間（Asia/Tokyo）の暦で行う。現在時刻はアプリケーション層の `Clock` から受け取る。

| 番号 | ルール | 実装 |
| --- | --- | --- |
| BR-01 | **発売月の超過**: 発売月の翌月 1 日 0:00 になったら超過とする（例: 発売月 2026-11 は 2026-12-01 0:00 から超過） | `isProductArchived` |
| BR-02 | **予約済の自動遷移**: 発売月を超過したら購入済にし、延期の確認待ちにする。受注期限は見ない | `determineAutomaticTransition` |
| BR-03 | **検討中の自動遷移**: 受注期限の翌日 0:00 になるか、発売月を超過したら未購入にする（受注期限がまだ先でも、発売月を超過したら未購入）。延期の確認待ちにはしない | `determineAutomaticTransition` |
| BR-04 | **購入済・未購入**: 自動では変えない（手で購入済にした商品は延期の確認の対象外） | `determineAutomaticTransition` |
| BR-05 | **アーカイブ**: 発売月が当月より前の商品は、ステータスにかかわらずアーカイブとする。アーカイブかどうかは保存せず、その都度求める | `isProductArchived`・`splitProductsByArchive` |
| BR-06 | **リストに戻すときのステータス**: 変更履歴の最後のステータスの変更が自動遷移なら、その変更前のステータスに戻す。最後の変更が利用者の操作なら、今のステータスのまま | `determineStatusBeforeAutomaticTransition` |
| BR-07 | **新しい発売月**: リストに戻す・延期の確認の「延期された」で指定する発売月は、当月以降とする | `restoreProduct`・`answerDeliveryConfirmation` |
| BR-08 | **アーカイブされた商品の編集**: 発売月以外は編集できる。発売月は編集では変えられず、リストに戻すで変える。編集でステータスを変えたら延期の確認待ちを外す | `updateProduct` |
| BR-09 | **カテゴリーの定義が正**: 商品に新しく設定できるのは、定義にあるカテゴリーだけ。商品には ID と、設定したときの名前を保存する | `createProduct`・`updateProduct` |
| BR-10 | **カテゴリー名の表示**: 定義にある ID は定義の今の名前で、定義にない ID は最後に保存した名前で示す（画面では「（定義にない）」を付ける） | `listProducts`・`buildCategoryFilterOptions` |
| BR-11 | **壊れた定義**: 定義のファイルに誤りがある間は、カテゴリーの設定と絞り込みはできない（理由を画面に表示する）。カテゴリーを変えない編集と、カテゴリーのない登録はできる。壊れたファイルは書き換えない | `readCategories`・`resolveCategory` |
| BR-12 | **絞り込み**: 選んだカテゴリーの商品だけを表示し、見出しの個数と合計金額も絞り込んだ商品で数える。何も選ばなければすべて。選択は端末ごとに覚え、選択肢にないものは選んでいないものとする | `filterProductsByCategory`・`useCategoryFilter` |
| BR-13 | **発売月の移動**: 移動できるのはアーカイブされていない商品だけで、移動先は当月以降。同じ月への移動は何もしない（履歴も記録しない）。変更は利用者の操作として記録する | `moveProductToReleaseMonth` |
| BR-14 | **カテゴリーの管理は最新の定義に対して**: 追加・改名・削除は、変更する時点の定義のファイルを読み直して行い、手で編集した内容（ID のないカテゴリー・ほかの項目）を残す。新しいカテゴリーは末尾に加える。名前は定義の中で重複させない。改名・削除するカテゴリーが最新の定義にない場合は変更しない | `addCategory`・`renameCategory`・`deleteCategory`（定義のファイル） |
| BR-15 | **改名への追従**: 改名したら、そのカテゴリーの商品に保存している名前も新しい名前にする（更新日時は変えない） | `renameCategory` |
| BR-16 | **カテゴリーの削除**: そのカテゴリーの商品（アーカイブを含む）を、移す先（定義のほかのカテゴリー）かカテゴリー未設定にしてから、定義から取り除く。移した商品の更新日時は移した時刻にする。カテゴリーの付け替えは変更履歴（ステータス・発売月）に記録しない | `deleteCategory` |
| BR-17 | **定義にないカテゴリー**: 定義にない ID の商品は、「定義に追加する」（同じ ID と、商品に最後に保存した名前で末尾に加える。同じ名前が定義にあれば加えない）か、すべての商品を定義のカテゴリーに移す・カテゴリー未設定にする | `addUndefinedCategoryToDefinition`・`reassignUndefinedCategoryProducts` |
| BR-18 | **認証が必要な範囲**: 認証が有効なときは、`/api/health` と `/api/auth/*` 以外の API にログインを求める。画面のファイル（HTML・JS・CSS）は認証なしで返し、画面がログインの画面を表示する（データはすべて API から取る）。認証が無効なときは誰でも使える | `createAuthenticationRequirement` |
| BR-19 | **アカウントは1つ**: アカウントがないときだけ作れる（ID は前後の空白を除いて1〜50文字、パスワードは8〜128文字）。2つ目は作れない | `setUpAccount` |
| BR-20 | **ログインした状態の期間**: 最後に使ってから30日。使うたびに延ばし、Cookie の有効期間も付け直す。30日使わなかった状態は使えない | `verifySession`・`isSessionExpired` |
| BR-21 | **総当たり対策**: ログインに5回続けて失敗すると、5回目の失敗から15分間、ID とパスワードが正しくてもログインできない。成功すると数え直す。ID が誤りの失敗も数える（アカウントが1つのため、アプリ全体で数える）。失敗の記録はメモリに持ち、再起動で数え直す | `recordLoginFailure`・`findLoginLockEnd` |
| BR-22 | **失敗の理由を示さない**: ID が誤りの場合もパスワードが誤りの場合も、同じ応答を返す。ID が誤りの場合もパスワードの比較と同じだけ時間をかける | `logIn` |
| BR-23 | **アカウントの消去**: パスワードを忘れた場合は、コマンド（`npm run reset-account`）でアカウントとすべてのログインした状態を消す。商品・カテゴリーなどは消さない | `resetAccount` |
| BR-24 | **入力項目の出し入れ**: 出し入れする項目は、送料・メーカー・受注期限・キャンセル可否・場所・開催日時と終了日時（1 組）・手数料・交通費（見込）・その他費用。表示するのは、カテゴリーで有効な項目と、編集のモーダルを開いた時点で値が保存されている項目（キャンセル可否は「可」、開催日時と終了日時はどちらかに値がある場合）。カテゴリー未設定・定義にないカテゴリーは既定（送料・メーカー・受注期限・キャンセル可否）、定義を読めない間はすべてを有効とする。表示していない項目は未入力として送る。出し入れは画面だけで行い、API は値を拒否しない（定義は手で変わり得るため） | `determineVisibleCategoryFields`（画面） |
| BR-25 | **合計金額**: 見出しの合計は、金額・送料・手数料・交通費（見込）・その他費用の合計。金額が未入力の商品は個数だけに含め、費用も合計に含めない。未購入は含めない。開催日時は関係しない | `summarizeProducts`（画面） |
| BR-26 | **「その他費用」の名前**: カテゴリーごとに持ち（1〜20 文字。既定は「その他費用」）、商品には保存しない。カテゴリー未設定・定義にないカテゴリー・定義を読めない場合は「その他費用」 | `resolveOtherExpenseLabel`（画面） |
| BR-27 | **項目の設定の変更**: 画面からの変更は、変える時点の定義のファイルを読み直し、変えた項目だけを反映する（手で編集した内容を残す）。項目を変えたカテゴリーには有効な項目をすべて書き、名前を既定に戻すと名前を取り除く。項目の指定がないカテゴリー（今までの定義・画面で追加したカテゴリー）は既定とする。商品に保存されている値は変えない | `updateCategoryFieldSettings`（定義のファイル） |
| BR-28 | **開催日時の表示**: 開催日時と終了日時の両方があるときだけカードに示す。カードを並べる幅では日本時間の日時（「11/20 18:00〜21:00」。同じ日なら終了の日付を省き、年が変わるなら年も）、スマートフォンの幅のリスト形式では開催期間。期間は分を 30 分単位で四捨五入（半分は切り上げ、最小 0.5 時間）し、それが 24 時間以上（23 時間 45 分以上）なら 12 時間単位で四捨五入した日数で示す（「約1.5時間」「約2日」。整数なら小数を付けない） | `formatEventPeriod`・`formatEventDuration`（画面） |

カテゴリーの改名・削除では、商品の更新と定義のファイルの書き込みを 1 つのトランザクションの中で行い、ファイルの書き込みを最後にする（書き込みに失敗したら商品の更新を取り消す）。

## 3. F-02 ステータスの自動遷移

- 判定の時期: 商品の一覧を取得するたび（`GET /api/products`）と、サーバーの起動時
- 遷移した場合は、変更履歴に種類「自動遷移」（`automatic`）、変更日時は判定した時刻で記録する
- 遷移の対象がなければ何も記録しない（何度一覧を取得しても履歴は増えない）
- 1 商品の遷移（ステータスの更新・履歴・延期の確認待ち）は 1 つのトランザクションで行う

```
            発売月を超過（BR-02）
  予約済 ─────────────────────────→ 購入済 ＋ 延期の確認待ち
            受注期限の翌日 or 発売月を超過（BR-03）
  検討中 ─────────────────────────→ 未購入
```

## 4. F-04 リストに戻す

1. 商品がアーカイブされていなければ拒否する（409 `PRODUCT_NOT_ARCHIVED`）
2. 新しい発売月が当月より前なら拒否する（400 `RELEASE_MONTH_IN_PAST`。BR-07）
3. ステータスを BR-06 で求め、発売月を新しい月にし、延期の確認待ちを外す。変更は利用者の操作（`user`）として記録する

## 5. F-05 延期の確認

| 回答 | 結果 |
| --- | --- |
| 届いた（`arrived`） | 購入済のまま（アーカイブに残る） |
| 延期された（`postponed`） | 新しい発売月（当月以降。BR-07）で予約済にする（リストに戻る） |
| 買わなかった（`notPurchased`） | 未購入にする（アーカイブに残る） |

- いずれの回答でも延期の確認待ちを外す。変更は利用者の操作（`user`）として記録する
- 確認待ちでない商品への回答は拒否する（409 `DELIVERY_CONFIRMATION_NOT_PENDING`）
- 画面は回答した商品だけを送る。回答しなかった商品は確認待ちのまま残り、次に開いたときにまた確かめる

## 6. API

| メソッド・パス | 内容 | 成功 |
| --- | --- | --- |
| `GET /api/products` | 自動遷移を反映した一覧。各商品に `deliveryConfirmationPending`（延期の確認待ちか）を含める | 200 `{ products }` |
| `POST /api/products` | 登録 | 201 |
| `PUT /api/products/:productId` | 編集（全項目） | 200 |
| `DELETE /api/products/:productId` | 削除 | 204 |

商品の登録・編集の本文ではカテゴリーを `categoryId`（未設定は `null`）で送り、応答では `categoryId` と `categoryName` を返す（#10）。場所・費用は `location`・`handlingFee`・`travelExpense`・`otherExpense`、開催日時・終了日時は `eventStartsAt`・`eventEndsAt`（UTC の ISO 8601）で送受する（#26・PR #30）。

## 7. F-08 認証

- **設定**: 設定ファイルの `authenticationEnabled`（環境変数 `WADERS_AUTHENTICATION_ENABLED` が優先。`true`・`false` のみ）。ひな形では `false`（issue #33）。項目がない既存の設定ファイルは有効として扱う（安全側に倒す）
- **パスワードの保存**: `crypto.scrypt`（N = 16384、r = 8、p = 1、ソルト 16 バイト、長さ 32 バイト）のハッシュ値を、パラメーターとソルトと一緒に保存する。比較は `timingSafeEqual`
- **ログインした状態**: 乱数 32 バイトの値を Cookie `waders_session` に入れる（`HttpOnly`・`SameSite=Strict`・`Path=/`・`Max-Age` 30日）。DB にはその値の SHA-256 だけを保存する。HTTPS の仕組みがないため `Secure` は付けない
- **CSRF**: 状態を変えるリクエスト（ログイン・ログアウトを含む）は `Content-Type: application/json` を必須にする（既存の決まり）。Cookie は `SameSite=Strict`
- **同時のログイン**: ログインの試行は1つずつ順に処理する（同時に送られた試行で BR-21 の回数をすり抜けさせない）
