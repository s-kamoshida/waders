# PR の本文のひな形

読むのは PR のレビュアー（人）。短く、判断に必要なことだけを書く。

## テストレビュー用（手順6。下書き PR の本文）

```markdown
## 目的
<issue の問題と、その原因（1〜3行）>

## 要件
<追記した要件の要約。コミット <ハッシュ>>

## テスト（<ファイル名>）
| テスト名 | 対応する要件 |
|---|---|
| <〜の場合、〜する> | <要件の該当箇所 / F-xx / BR-xx> |

## 私が決めたこと（違えば指摘してください）
- <issue や確認の回答から決まらなかった点と、選んだ既定>

## テストにしていない振る舞い
- <アニメーションの見た目など、テストで確かめられないもの。実装後にどう確かめるか>

## レビューのお願い
テストが要件どおりか、抜けている振る舞いがないかを見てください。
承認は「Files changed」タブ右上の **Review changes → Approve → Submit review** でお願いします（会話欄のコメントは承認として記録されません）。
**承認後もマージはしないでください。** 実装をこの PR に追加してから、改めてレビューとマージをお願いします。

Refs #<番号>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

## 実装レビュー用（手順9。PR へのコメント）

```markdown
実装しました。レビューをお願いします。

## 変更内容
- <ファイル>: <何を変えたか>

## 確認したこと
- `npm run check`（型チェック・ESLint・全 <件数> 件のテスト）が通過
- <実際に起動して確かめたこと>

## 未確認
- <確かめられなかったこと。なければ「なし」>

## 気になっている点
- <見送った改善、既知の制約など。なければ省略>
```
